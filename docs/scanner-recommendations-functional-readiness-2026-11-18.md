# Готовность сканера и рекомендаций

Дата оценки: 18.11.2026

## Итоговый процент

**Готовность функционального пакета к production-релизу: 55%.**

Это не процент написанного кода. Оценка учитывает четыре равных блока: реализация и автоматические тесты, безопасное поведение и provenance, приёмочные данные/ручной smoke-тест, а также подтверждение production-развёртывания. Последние два блока пока не закрыты полностью, поэтому зелёные локальные проверки сами по себе не дают 100%.

Отдельно:

- **Сканер: 70% функциональной готовности.** Реализация и локальные проверки близки к завершению, но остаются corpus из 30+ обезличенных изображений, ручная проверка на iOS/Android/desktop и приёмка после развёртывания.
- **Рекомендации: 40% функциональной готовности.** Механизм правил, provenance и предупреждения реализованы, однако данные для конкретных автомобилей не подтверждены официальными руководствами.
- **Готовность к ограниченному локальному использованию: 80%.** Можно проверять общий поток сканирования и общие safety-подсказки при обязательной ручной проверке результата.

## Что делает сканер

Поток BarcodeScannerScreen принимает код с камеры, из фотографии или из тестового preset:

1. Нативный BarcodeDetector пытается распознать QR, Code 128/39, EAN/UPC, Data Matrix и другие поддержанные форматы.
2. При отсутствии или ошибке нативного API используется лениво загружаемый ZXing fallback; QR дополнительно проходит через jsQR fallback.
3. Распознанный текст проходит через parseBarcodeOrQr:
   - VIN валидируется по длине и запрещённым символам I/O/Q;
   - WMI используется только для страны и производителя, без выдумывания модели и года;
   - модель и год заполняются автоматически только при точном совпадении VIN с автомобилем в гараже;
   - известный артикул берётся из каталога;
   - неизвестный код остаётся scanType: unknown без выдуманной цены, наличия или детали.
4. Проверка складских остатков и цен вызывается только для известной каталожной детали.
5. Применимость детали показывается как подтверждённая только при явном совпадении варианта в compatibleModels; в остальных случаях пользователь видит предупреждение.
6. VIN можно передать в форму автомобиля. Для нового VIN открывается добавление автомобиля с заполненным VIN, а для точного совпадения открывается редактирование соответствующей записи.
7. При переносе неизвестного кода в форму цена остаётся пустой и должна быть введена вручную; демонстрационная цена не подставляется.

## Что делает слой рекомендаций

src/catalog/recommendations.ts фильтрует проверяемые правила по марке, типу топлива, пробегу и поисковому запросу. API возвращает текст совета, риск, ссылки на источники, confidence и пояснение применимости. Интерфейс явно различает:

- общую рекомендацию;
- совет, который требует сверки с руководством;
- подтверждённую рекомендацию для конкретной комплектации.

Ссылка на сайт производителя считается provenance и точкой входа, но не доказательством того, что конкретный документ уже проверен для года, рынка, двигателя и коробки.

## Почему рекомендации ещё не готовы для каждого автомобиля

npm run catalog:audit сейчас показывает:

- 110 конфигураций в каталоге;
- 100 со статусом provisional;
- 10 со статусом partially_verified;
- 0 полностью авторитетно подтверждённых конфигураций;
- 110 конфигураций с отсутствующими evidence;
- 110 конфигураций с неизвестной совместимостью.

В репозитории нет загруженных PDF/Word-сервисных руководств. Есть реестр ссылок производителей, два общих knowledge-фрагмента и пилотные legacy-evidence. Поэтому сейчас нельзя утверждать, что интервалы ТО, объёмы жидкостей, моменты затяжки или fitment подтверждены для каждого автомобиля.

Для первой подтверждённой модели требуется получить документ с точным рынком, годом, двигателем, коробкой и комплектацией, затем импортировать только проверенные выдержки с documentHash, страницей/разделом и provenance. После этого отдельные правила можно повысить до high только в пределах покрытой конфигурации.

## Проверки, выполненные локально

- npm run lint — успешно.
- npm test — 33 файла, 184 теста, успешно.
- npm run test:scanner — 5 файлов, 39 тестов, успешно.
- npm run build — успешно.
- npm run config:check — 36 ключей, успешно.
- npm run catalog:audit — успешно, но с указанными выше provisional/partial статусами.
- npm audit --omit=dev — 0 уязвимостей.
- git diff --check — успешно.

Эти проверки относятся к рабочей копии и не означают, что последние изменения уже развернуты в Cloud Run или Worker.

## Что нужно для 100%

1. Прогнать приёмочный набор минимум из 30 обезличенных фотографий с ground truth и зафиксировать целевые метрики VIN/штрихкодов/документов.
2. Выполнить ручной smoke-тест камеры и загрузки фото на iOS, Android и desktop.
3. Проверить повторяемость, параллельные декодирования, лимиты размера файла и поведение при отказе камеры/провайдера.
4. Получить и проверить первое официальное руководство для конкретного рынка и комплектации.
5. Импортировать выдержки с SHA-256, страницей/разделом и provenance; добавить тесты применимости по году, двигателю, коробке, приводу, кузову и рынку.
6. После прохождения локальных и внешних gates собрать, развернуть и проверить именно этот commit, затем сохранить health, rollback и observation evidence.

До закрытия этих пунктов рекомендации следует показывать как общие или требующие проверки по руководству. Нельзя объявлять их готовыми для каждого автомобиля.
