# Готовность сканера и рекомендаций

Дата оценки: 19.11.2026

## Итоговый процент

**Готовность функционального пакета к production-релизу: 55%.**

Это не процент написанного кода. Оценка учитывает четыре равных блока: реализация и автоматические тесты, безопасное поведение и provenance, приёмочные данные/ручной smoke-тест, а также подтверждение production-развёртывания. Последние два блока пока не закрыты полностью, поэтому зелёные локальные проверки сами по себе не дают 100%.

Отдельно:

- **Сканер: 70% функциональной готовности.** Реализация и локальные проверки близки к завершению, но остаются corpus из 30+ обезличенных изображений, ручная проверка на iOS/Android/desktop и приёмка после развёртывания.
- **Рекомендации: 45% функциональной готовности.** Механизм правил, provenance и предупреждения реализованы; две проверенные выдержки теперь доступны для одной точной конфигурации Nissan X-Trail T32-A (Таиланд, 2014, MR20DD, CVT). Покрытие каталога остаётся узким.
- **AI-диагностика:** маршрут `/api/ai/diagnose` получает профиль автомобиля, историю последних пяти записей и симптомы; в prompt передаются RAG-выдержки, справка серии и их тип доказательности. Ответ проходит структурную проверку, а источники прикрепляются сервером. Реальный внешний вызов модели зависит от настроенного Vertex/Gemini доступа.
- **Готовность к ограниченному локальному использованию: 80%.** Можно проверять общий поток сканирования и общие safety-подсказки при обязательной ручной проверке результата.

## Что делает сканер

Поток BarcodeScannerScreen принимает код с камеры, из фотографии или из тестового preset:

1. Нативный BarcodeDetector пытается распознать QR, Code 128/39, EAN/UPC, Data Matrix и другие поддержанные форматы.
2. При отсутствии или ошибке нативного API используется лениво загружаемый ZXing fallback; QR дополнительно проходит через jsQR fallback.
3. Распознанный текст проходит через parseBarcodeOrQr:
   - VIN валидируется по длине и запрещённым символам I/O/Q;
   - WMI используется только для страны и производителя, без выдумывания модели и года;
   - модель и год заполняются автоматически только при точном совпадении VIN с автомобилем в гараже;
   - известный артикул берётся из каталога;
   - неизвестный код остаётся scanType: unknown без выдуманной цены, наличия или детали.
4. Проверка складских остатков и цен вызывается только для известной каталожной детали.
5. Применимость детали показывается как подтверждённая только при явном совпадении варианта в compatibleModels; в остальных случаях пользователь видит предупреждение.
6. VIN можно передать в форму автомобиля. Для нового VIN открывается добавление автомобиля с заполненным VIN, а для точного совпадения открывается редактирование соответствующей записи.
7. При переносе неизвестного кода в форму цена остаётся пустой и должна быть введена вручную; демонстрационная цена не подставляется.

## Что делает слой рекомендаций

src/catalog/recommendations.ts фильтрует проверяемые правила по марке, типу топлива, пробегу и поисковому запросу. API возвращает текст совета, риск, ссылки на источники, confidence и пояснение применимости. Интерфейс явно различает:

- общую рекомендацию;
- совет, который требует сверки с руководством;
- подтверждённую рекомендацию для конкретной комплектации.

Ссылка на сайт производителя считается provenance и точкой входа, но не доказательством того, что конкретный документ уже проверен для года, рынка, двигателя и коробки.

## Почему рекомендации ещё не готовы для каждого автомобиля

npm run catalog:audit сейчас показывает:

- 110 конфигураций в каталоге;
- 100 со статусом provisional;
- 10 со статусом partially_verified;
- 0 полностью авторитетно подтверждённых конфигураций;
- 110 конфигураций с отсутствующими полными evidence каталога;
- две документальные выдержки покрывают одну точную конфигурацию T32-A/TH/2014/MR20DD/CVT; остальные 109 конфигураций не имеют полного покрытия инструкциями.

В репозитории есть один загруженный PDF руководства и реестр ссылок производителей, два общих knowledge-фрагмента и пилотные legacy-evidence. Две проверенные выдержки из загруженного руководства доступны только для Nissan X-Trail T32-A, TH, 2014, MR20DD/CVT. Нельзя утверждать, что интервалы ТО, объёмы жидкостей, моменты затяжки или fitment подтверждены для каждого автомобиля.

Для расширения покрытия нужно получать документы с точным рынком, годом, двигателем, коробкой и комплектацией, затем импортировать только проверенные выдержки с documentHash, страницей/разделом и provenance. Повышать правила до high можно только в пределах покрытой конфигурации.

- npm run lint — успешно.

- npm run build — успешно.
- npm run config:check — 36 ключей, успешно.
- npm run catalog:audit — успешно, но с указанными выше provisional/partial статусами.
- npm run catalog:recommendations — успешно: 200 моделей, 110 конфигураций, 1 550 проверок рекомендаций, 3 770 market/year-проверок по каждому указанному году производства и 4 217 ссылок на источники; ошибок применимости и provenance не найдено. Матрица поведения зелёная, но все 110 конфигураций всё ещё не имеют полного evidence конфигурации.
- npm audit --omit=dev — 0 уязвимостей.
- git diff --check — успешно.
- npm run release:readiness with `GARAGE_PUBLIC_URL=https://garageai.site` — 13 local checks passed, 0 failed; production database preflight and production configuration contract are pending because this is not a controlled production environment. Nine external gates remain pending, including full OEM evidence for every catalog configuration. The JSON summary counts all pending gates and exposes local and external counts separately. Database connection details are suppressed from the readiness output.
- `npm run production:config-check` passes with safe test values for HTTPS URLs, proxy settings, PostgreSQL flags, email authentication and Vertex configuration; no credential values are printed. In the normal workstation process the corresponding readiness gate remains pending because production secrets are intentionally absent.
- HTTP integration test now verifies server-start corpus loading, both source excerpts, citations, and rejection of document evidence for T31/RU/2008, the wrong market/year/engine, and e-CVT.
- Release-readiness теперь включает отдельный gate Recommendation matrix по всем 200 моделям и 110 конфигурациям, с 3 770 market/year-комбинациями, положительным Nissan T32-A и отрицательными сценариями без точного совпадения.

Аудит AI-диагностики выявил и исправил ложную точность: prompt и API-тип больше не запрашивают confidence или вероятности причин, валидатор принимает причины как гипотезы без псевдостатистических оценок, а sanitizer продолжает удалять такие поля, если модель их вернёт. Изменение проверено: 35 файлов, 197 тестов, TypeScript и production build прошли. Добавление результата в To-Fix не создаёт выдуманную стоимость, пробег или категорию подвески. Safety-оценка показывается пользователю и сохраняется в описании задачи. Для мобильного экрана истории убрана фиксированная задача про охлаждение, не связанная с фактическими данными.

Дополнительно API теперь удаляет из ответа AI-сгенерированные цены и рекомендуемые детали/артикулы, поскольку в приложении нет верифицированного источника цены и fitment. Диагностический маршрут не пишет текст исключения провайдера в логи.

После добавления корпуса выполнен runtime smoke test на отдельном локальном экземпляре: источник вернул 2 принятых фрагмента; для совпадающей конфигурации API вернул документальную рекомендацию с цитатой, а для X-Trail T31/RU/2008 — ни одной документальной выдержки.

Эти проверки относятся к рабочей копии и не означают, что последние изменения уже развернуты в Cloud Run или Worker. Публичный health текущего домена проверен отдельно; production preflight в текущем окружении блокируется отсутствием `DATABASE_URL`, PostgreSQL fail-closed guard не обходился. Release-readiness теперь автоматически запускает preflight только при наличии этой переменной в окружении процесса и не печатает строку подключения или детали ошибки соединения.

## Что нужно для 100%

1. Прогнать приёмочный набор минимум из 30 обезличенных фотографий с ground truth и зафиксировать целевые метрики VIN/штрихкодов/документов.
2. Выполнить ручной smoke-тест камеры и загрузки фото на iOS, Android и desktop.
3. Проверить повторяемость, параллельные декодирования, лимиты размера файла и поведение при отказе камеры/провайдера.
4. Получить и проверить первое официальное руководство для конкретного рынка и комплектации.
5. Импортировать выдержки с SHA-256, страницей/разделом и provenance; добавить тесты применимости по году, двигателю, коробке, приводу, кузову и рынку.
6. После прохождения локальных и внешних gates собрать, развернуть и проверить именно этот commit, затем сохранить health, rollback и observation evidence.

До закрытия этих пунктов рекомендации следует показывать как общие или требующие проверки по руководству. Нельзя объявлять их готовыми для каждого автомобиля.
