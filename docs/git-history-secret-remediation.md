# Устранение секретов из Git history

Статус: runbook для отдельного согласованного окна работ. Документ не разрешает и не запускает перепись истории сам по себе.

## Что требуется устранить

Gitleaks подтверждает шесть исторических значений `tokenHash`/`csrfSecret` в `data/sessions.json` из коммитов `433a567` и `b24b8e5`. Это реальные данные сессий, а не ложные срабатывания. Их нельзя игнорировать через allowlist.

Файл уже находится в `.gitignore`; цель — удалить его из всех достижимых Git refs и сделать прежние значения недействительными. Не публикуйте сами значения в issue, PR, логах CI или командной строке.

## Preconditions

Перед началом ответственный за репозиторий должен подтвердить:

1. Окно обслуживания и разрешение временно допустить force-push в защищённые ветки.
2. Список владельцев всех clones, fork и CI cache, которым надо перейти на новую историю.
3. Ротацию всех потенциально затронутых production-сеансов и секретов до публикации переписанной истории. В приложении используйте штатный `npm run revoke:sessions` только в контролируемой production-среде с резервной копией данных.
4. Что легитимные данные хранилища находятся вне Git и имеют проверенную резервную копию. Git-версия `data/sessions.json` не является источником для восстановления production-данных.
5. Свежий backup репозитория и возможность отката прав доступа/деплоя. Откат содержания старой истории не допускается: он снова опубликует секреты.

## Процедура в изолированной административной копии

Запускайте это только в новом зеркальном clone вне рабочего каталога разработки. Не добавляйте секреты в shell history и не используйте общий компьютер.

```powershell
git clone --mirror https://github.com/AlEX91udemy/GarageAI_1.0.git GarageAI_1.0-history-remediation.git
Set-Location GarageAI_1.0-history-remediation.git
git bundle create ../GarageAI_1.0-before-history-remediation.bundle --all
git fsck --full
```

Установите `git-filter-repo` из доверенного источника и удалите только исторический файл сессий из всех refs:

```powershell
git filter-repo --force --path data/sessions.json --invert-paths
git fsck --full
git log --all -- data/sessions.json
```

Последняя команда не должна вывести коммиты. Затем выполните секрет-сканирование переписанного зеркала с тем же Gitleaks, что использует CI. Не загружайте отчёт с исходными значениями в GitHub.

Только после зелёного сканирования и подтверждённой ротации секретов администратор может force-push переписанных веток и тегов. Снимите/настройте branch protection заранее, а после публикации сразу верните защиту. Созданные до этого PR с переписанными коммитами следует закрыть и создать заново от актуальной `main`.

## После публикации

1. Запустите CI на `main` и на новом PR: Gitleaks, Node/PostgreSQL/HTTP, Python audit и Cloudflare dry run должны быть зелёными.
2. Все разработчики должны сделать свежий clone. Не используйте `git pull` для старого clone и не push-ьте старые refs.
3. Очистите кэши CI и попросите владельцев forks переписать/удалить refs, содержащие прежнюю историю.
4. Проверьте, что `.gitignore` сохраняет `data/sessions.json` исключённым, и выполните production smoke после ротации сессий.
5. Сохраните backup bundle в ограниченном хранилище на согласованный срок. Он содержит старую историю и должен рассматриваться как чувствительный артефакт.

## Критерий завершения

Работа завершена только когда в доступной истории нет `data/sessions.json`, Gitleaks проходит без suppressions, активные сессии/секреты ротированы, а CI и production smoke подтверждены.
